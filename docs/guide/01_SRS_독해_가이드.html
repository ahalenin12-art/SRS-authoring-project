먼저 알아둘 것. SRS-002는 "무엇을 만들 것인가"를 정하는 문서가 아닙니다. 그건 PRD와 앞선 SRS가 이미 했습니다. 이 문서는 "정해진 기술로 그걸 어떻게 만족시키는가"만 다룹니다. 그래서 읽다가 "왜 이 기능이 필요하지?"라는 의문이 들면, 답은 이 문서가 아니라 PRD에 있습니다.

1부 · 용어 해설집 ①

가장 먼저 걷어야 할 안개입니다. "프론트엔드", "백엔드", "풀스택"은 서로 다른 물건이 아니라 같은 앱의 다른 위치를 부르는 말입니다.

심화

왜 "App" Router인가. Next.js에는 두 가지 라우팅 방식이 있습니다. 예전 방식인 Pages Router와 지금의 App Router입니다. App Router는 서버 컴포넌트를 기본으로 삼는다는 점이 결정적으로 다릅니다. 즉 화면을 구성하는 코드가 기본적으로 서버에서 실행되고, 필요한 부분만 골라서 브라우저로 내려보냅니다.

이 프로젝트에서 이게 왜 중요하냐면 — 밴드 계산이나 병목 종목 지목 같은 로직이 브라우저에 노출되면 안 되기 때문입니다. SRS-002의 SRS-FR-019는 "병목 종목은 서버가 지정한다"를 요구사항으로 못박았습니다.

심화

Server Action은 사실 숨겨진 POST 엔드포인트입니다. Next.js가 빌드 시점에 각 액션에 고유한 ID를 부여하고, 클라이언트에서 호출하면 프레임워크가 알아서 POST 요청을 만들어 보냅니다. 개발자 눈에는 그냥 함수 호출처럼 보이지만 실제로는 네트워크를 탑니다.

그래서 SRS-002의 TEC-ACT-003이 "클라이언트 검증 결과를 신뢰하지 않는다"를 요구사항으로 못박았습니다. 함수처럼 생겼다고 안전한 게 아니라, 누구든 그 엔드포인트를 직접 때릴 수 있기 때문입니다.

'use server'   // ← 이 한 줄이 파일 전체를 서버 전용으로 만든다

export async function submitTransfer(input) {
  // 여기 코드는 브라우저에 절대 내려가지 않는다
  // 하지만 input 은 클라이언트가 보낸 것 → 반드시 재검증
}

심화

스키마 레벨 제약이 이 문서의 핵심 발상입니다. SRS-002 §5.3은 논리 규칙을 DB 제약으로 내려서 강제합니다.

-- 감사 로그는 절대 수정·삭제 불가 (WORM)
REVOKE UPDATE, DELETE ON "AuditLog" FROM app_role;
CREATE TRIGGER audit_log_immutable BEFORE UPDATE OR DELETE ...

-- 밴드는 시작일 ≤ 종료일
ALTER TABLE "LockWindow" ADD CONSTRAINT band_order
  CHECK (end_band_from <= end_band_to);

-- 같은 전문을 두 번 처리할 수 없음 (멱등성)
@@unique([transferId, stageNo, messageSeq])

왜 이렇게까지 하냐면 — 코드는 사람이 실수할 수 있지만 DB 제약은 실수를 허용하지 않기 때문입니다. 감사 로그를 지우는 코드를 누가 실수로 짜도, DB가 거부합니다.

이걸 규칙 강제 수단으로 씁니다. 다음 카드를 보세요.

이 장에서 가장 영리한 부분. PRD는 "완료일을 단일 날짜로 표시하지 말 것"을 여러 번 요구합니다. 화면이 12개인데, 개발자가 한 곳에서만 실수해도 규칙이 깨집니다.

SRS-002는 <BandDisplay>라는 전용 컴포넌트를 만들고, 그 컴포넌트의 타입에 "단일 날짜" 자리를 아예 정의하지 않았습니다. 단일 날짜를 넣으려는 코드는 작성하는 순간 오류가 납니다. 코드 리뷰까지 갈 필요도 없습니다.

심화 
// components/domain/band-display.tsx
type BandDisplayProps = {
  endBandFrom: Date          // 시작
  endBandTo: Date            // 종료
  businessDaysMin: number
  businessDaysMax: number
  approximate?: boolean      // 폴백 시 "대략치입니다" 병기
}
// endDate 같은 prop 이 타입에 없다 → 컴파일 실패로 위반 차단

같은 방식으로 <StatusLabel>(내부 코드 노출 차단), <MoneyText>(비율 단독 표기 차단), <MaskedAccount>(계좌번호 마스킹)가 있습니다. 규칙을 사람의 주의력이 아니라 도구에 맡기는 설계입니다.

품질을 재는 말들

PM이 가장 자주 마주칠 용어들입니다. 특히 p95와 멱등성은 회의에서 그냥 나옵니다.

p9595 백분위
쉽게 말하면
100번 중 95번은 이 시간 안에 끝난다는 뜻. 나머지 5번은 더 걸립니다.

평균은 느린 소수를 숨깁니다. 99명이 0.1초, 1명이 10초여도 평균은 0.2초입니다. p95는 그 1명을 드러냅니다.

왜 금융에서 필수인가
네트워크는 끊깁니다. 재시도도 합니다. 멱등성이 없으면 이체가 두 번 나갑니다.

심화

멱등성은 "재시도해도 안전한가"를 묻는 질문입니다. HTTP 메서드로 보면 GET·PUT·DELETE는 본래 멱등이고 POST는 아닙니다. 그런데 이 프로젝트의 전송·예약은 POST 성격인데 멱등이어야 합니다.

해법은 멱등 키입니다. 클라이언트가 요청마다 고유 ID를 만들어 보내고, 서버는 그 ID를 본 적 있으면 다시 처리하지 않고 최초 결과를 그대로 돌려줍니다.

// 전문 수신의 멱등 키 — DB 유니크 제약으로 강제
@@unique([transferId, stageNo, messageSeq])

// 고객 요청의 멱등 키 — 클라이언트가 생성
submitTransfer({ transferId, requestId, ... })

2부 · 핵심 개념 ①

왜 프론트와 백을 합쳤나

C-TEC-001·002가 이 프로젝트의 성격을 결정합니다. 보통은 나누는데, 여기서는 일부러 합쳤습니다.

분리 방식 (일반적)단일 풀스택 (이 프로젝트)
구성프론트엔드 앱 + 백엔드 서버 각각Next.js 앱 하나
팀프론트 팀 · 백엔드 팀한 팀
연결API 규격을 합의하고 맞춰야 함같은 코드베이스라 합의 불필요
배포각각 배포. 버전 맞춰야 함한 번에 배포
적합규모가 크고 팀이 나뉠 때빠르게 만들어 검증할 때

PM이 알아야 할 트레이드오프. 합치면 빠릅니다. 대신 나중에 규모가 커져 팀을 나눠야 할 때 분리 비용이 발생합니다. 지금은 Phase 0~1 검증 단계이므로 합치는 게 맞는 선택입니다.

다만 SRS-002는 미래를 위한 장치를 하나 심어뒀습니다 — 도메인 계산 로직을 순수한 별도 모듈로 격리했습니다. 나중에 백엔드를 분리하더라도 계산 코드는 그대로 옮길 수 있습니다.

심화

lib/domain/*은 Prisma를 import하지 않습니다(TEC-DOM-001). I/O가 전혀 없는 순수 함수 집합입니다.

이렇게 만든 실질적 이득이 두 가지입니다. 첫째, 단위 시험이 즉시 가능합니다 — DB 없이도 검증 데이터셋 6건을 돌릴 수 있어서 매 릴리스 자동 회귀가 성립합니다. 둘째, 같은 코드를 브라우저에서도 실행할 수 있습니다. 이게 §9.3 충돌의 해법이 됩니다.

2부 · 핵심 개념 ②

Server Action이냐 Route Handler냐

§4.1의 판정표입니다. 규칙은 간단합니다 — 누가 부르는가로 갈립니다.

Server Action

고객이 화면에서 부를 때

  • 로그인 세션이 이미 있음
  • 보안 처리를 프레임워크가 해줌
  • 화면 갱신을 같이 처리 가능

예약 저장 · 전송 · 취소 · 인출 시뮬레이션 (7개)

Route Handler

다른 시스템이 부를 때

  • 로그인 세션이 없음
  • 별도 인증이 필요
  • 응답 형식을 상대가 파싱함

매매창 판정 · 전문 수신 · 배치 4종 (7개)

이 구분이 왜 문서에 명시돼 있나. 둘 다 "서버에서 도는 코드"라 개발자마다 다르게 고를 수 있습니다. 기준이 없으면 비슷한 기능이 서로 다른 방식으로 구현되고, 보안 처리가 빠지는 자리가 생깁니다.

PM 관점에서는 이걸 "판단이 필요한 자리를 미리 없앤 것"으로 읽으면 됩니다. 좋은 기술 문서의 특징입니다.

2부 · 핵심 개념 ③

"로그를 못 남기면 전송도 취소한다"

SRS-002에서 가장 강한 요구사항 중 하나입니다. 처음 보면 과하게 느껴지는데, 이유가 있습니다.

상황

고객이 이체 전송 버튼을 누릅니다. 이때 화면에는 "8월 31일 ~ 9월 2일 완료 예정"이라고 떠 있었습니다. 시스템은 ① 감사 로그를 남기고 ② 상태를 "접수됨"으로 바꿔야 합니다.

만약 ②만 성공하고 ①이 실패하면

신청은 접수됐는데 기록이 없습니다. 나중에 완료가 늦어져 고객이 "9월 2일이라고 했잖아요"라고 하면, 회사는 그때 화면에 뭐가 떠 있었는지 증명할 방법이 없습니다. 밴드 값은 이후 재계산으로 계속 바뀌기 때문입니다.

그래서 둘을 한 묶음(트랜잭션)으로 처리합니다. 로그 적재가 실패하면 상태 변경도 되돌리고, 고객에게는 "다시 시도해 주세요"를 보여줍니다.

전송은 법적으로 전자적 의사표시입니다. 기록 없이 의사표시만 성립시키면 회사가 방어 수단을 잃습니다.

심화

주목할 점은 화면에 표시된 밴드 값을 클라이언트가 서버로 보낸다는 설계입니다. 보통은 클라이언트가 보낸 값을 믿지 않는 게 원칙인데, 여기서는 일부러 받습니다.

서버가 다시 계산하면 그 순간의 값이지 고객이 실제로 본 값이 아니기 때문입니다. 감사 로그에 남아야 하는 건 후자입니다.

await prisma.$transaction(async (tx) => {
  assertTransition(t.status, 'RECEIVED')   // 금지 전이 차단
  await tx.auditLog.create({ ... })        // 실패 시 전체 롤백
  await tx.transfer.update({
    where: { id, status: 'DRAFT' },        // 낙관적 동시성
    data:  { status: 'RECEIVED' },
  })
})
// 외부 전문 송신·알림은 트랜잭션 밖 — 실패해도 상태는 유지

2부 · 핵심 개념 ④

같은 요청이 두 번 와도 한 번만

멱등성입니다. 금융 시스템에서 이걸 놓치면 돈이 두 번 움직입니다.

상황왜 생기나멱등성 없으면
고객이 버튼 두 번 누름응답이 느려서 다시 누름신청이 2건
네트워크 끊김 후 재시도앱이 자동으로 재전송신청이 2건
같은 전문 2회 수신중계망이 재전송상태가 두 단계 건너뜀
배치가 중복 실행스케줄러 특성밴드 값이 흔들림

해법은 "이 요청 본 적 있나?"를 확인하는 것입니다. 요청마다 고유 번호를 붙이고, 이미 처리한 번호면 새로 처리하지 않고 처음 결과를 그대로 돌려줍니다.

SRS-002는 이걸 코드가 아니라 데이터베이스 제약으로 강제합니다. 같은 번호를 두 번 저장하려 하면 DB가 거부합니다. 개발자가 깜빡해도 막힙니다.

PM이 기억할 한 문장. "재시도해도 안전한가?" — 이 질문을 상태를 바꾸는 모든 기능에 대해 물어야 합니다. 답이 "아니오"면 사고가 날 자리입니다.

2부 · 핵심 개념 ⑤

서버리스가 주는 것과 가져가는 것

Vercel을 고른 대가입니다. 충돌 7건 중 4건이 여기서 나옵니다.

주는 것

  • 서버 관리가 필요 없음
  • 안 쓸 때 비용이 안 듦
  • 몰려도 알아서 늘어남
  • Git에 올리면 자동 배포

가져가는 것

  • 콜드 스타트 — 처음 깨는 데 시간이 듦
  • 실행 시간 한도 — 오래 도는 작업 불가
  • 상주 프로세스 없음 — "상시 감시" 불가
  • 커넥션 관리 — DB 접속이 폭증할 수 있음

가장 아픈 지점. PRD는 "잔고가 반영되면 60초 이내 알림"을 요구합니다. 그런데 서버리스에는 계속 지켜보는 프로세스가 없습니다. 정해진 주기로만 확인할 수 있습니다.

주기를 1분으로 잡아도 최악의 경우 60초를 넘깁니다. 그래서 SRS-002는 "원장 쪽에서 알려주는(push) 연동이 필요하다"고 결론 냈습니다. 이건 우리가 못 정하는 문제라 다른 팀에 요청해야 합니다.

심화

Cron 중복 실행 문제는 리더 선출 없이 멱등 갱신으로 풀었습니다. 조건을 UPDATE 문에 포함시켜 원자적으로 처리합니다.

await prisma.lockWindow.updateMany({
  where: { transferId, cachedOn: { lt: today } },  // ← 조건이 UPDATE 안에
  data:  { endBandFrom, endBandTo, cachedOn: today },
})
// 두 번째 실행은 cachedOn 이 이미 today 라 대상 0건

또 하나 — Vercel Cron은 UTC 기준입니다. 0 0 * * 1-5가 KST 09:00 월~금이 됩니다. 다만 공휴일은 Cron이 모릅니다. 그래서 핸들러 진입 직후 영업일 여부를 확인하고 아니면 즉시 반환합니다.

2부 · 핵심 개념 ⑥

규칙을 문서가 아니라 도구에 새긴다

SRS-002를 관통하는 설계 철학입니다. 이 하나만 이해해도 문서의 절반이 읽힙니다.

규칙약한 방법이 문서의 방법
완료일을 단일 날짜로 표시 금지문서에 적고 리뷰에서 확인컴포넌트 타입에 단일 날짜 자리를 안 만듦
감사 로그 수정·삭제 금지"고치지 마세요" 규칙DB가 UPDATE·DELETE를 거부
같은 전문 중복 처리 금지코드에서 확인 후 건너뜀DB 유니크 제약으로 저장 자체를 차단
본인 계좌만 조회코드에서 검사코드 + DB 행 단위 보안 이중
밴드는 시작일 ≤ 종료일계산 후 검증DB 제약으로 저장 불가

왜 이렇게까지 하나. 문서에 적힌 규칙은 사람이 읽고 기억해야 지켜집니다. 새 개발자가 오거나, 급한 수정이 들어가거나, 6개월 뒤 아무도 기억 못 할 때 깨집니다.

도구에 새긴 규칙은 깨뜨리려는 시도 자체가 실패합니다. 코드가 컴파일되지 않거나, DB가 저장을 거부합니다.

PM이 써먹을 수 있는 질문. 중요한 규칙을 이야기할 때 이렇게 물어보세요.
"이 규칙을 어기면 어느 단계에서 걸리나요? 코드 작성할 때? 리뷰할 때? 운영 중에?"

앞쪽일수록 안전합니다. "운영 중에 발견됩니다"라는 답이 나오면, 그 규칙은 언젠가 깨집니다.

2부 · 핵심 개념 ⑦

p95를 이해하면 성능 회의가 달라진다

"빨라야 한다"는 요구는 검증할 수 없습니다. p95는 그걸 검증 가능한 숫자로 바꾸는 도구입니다.

같은 데이터, 다른 결론

100명이 화면을 열었습니다. 95명은 0.3초 만에 봤고, 5명은 3초가 걸렸습니다.

  • 평균으로 보면 0.44초 — "괜찮네요"
  • p95로 보면 3초 — "5%가 3초를 기다립니다"

이 프로젝트의 p95 목표
홈 진행 카드 ≤ 0.8초 · 현황판 ≤ 1.2초 · 상태 조회 API ≤ 0.5초 · 인출 계산 ≤ 1초 · 인출액 변경 재계산 ≤ 0.3초

PM이 반드시 알아야 할 것 — 목표치와 알람은 다릅니다.

SRS-002는 두 숫자를 따로 관리합니다. 합격 기준은 "p95 ≤ 0.8초"이고, 운영 알람은 "p95가 1.0초를 10분 넘게 초과하면"입니다.

왜 나누냐면 — 알람이 합격 기준과 같으면 목표를 아슬아슬하게 지키는 동안 계속 울립니다. 그러면 사람들이 알람을 무시하기 시작합니다.

3부 · 제약 충돌

가장 위험한 두 건

1번과 2번입니다. 둘 다 기술로 완전히 풀리지 않고 다른 팀의 답이 필요합니다.

충돌 01 — 콜드 스타트가 정상 주문을 막는다

구조. 고객이 주식을 사려 하면, 주문 시스템이 우리에게 "이 계좌 지금 매매 가능한가?"를 묻습니다. 우리는 0.5초 안에 답해야 합니다.

문제. 서버가 꺼져 있었으면 깨우는 데만 그 시간을 다 씁니다. 답이 늦으면 시스템은 안전한 쪽인 "매매 불가"로 처리합니다.

결과. 이관과 무관한 정상 주문이 거부됩니다. 그리고 이건 "화면이 가능하다고 했는데 거부된" 사고로 집계되어, 즉시 롤백을 발동시키는 가드레일 지표(일간 0.1%)를 갉아먹습니다.

그나마 다행인 것. 실패 방향이 안전합니다. "막혔는데 열렸다고 표시"하면 주문이 나가버려 되돌릴 수 없지만, 반대는 고객이 다시 시도하면 됩니다. 설계가 의도적으로 이 방향을 골랐습니다.

충돌 02 — 60초 알림을 지킬 수 없다

구조. 돈이 계좌에 들어오면 60초 안에 알려야 합니다. 그래야 고객이 바로 매매를 재개할 수 있습니다.

문제. 서버리스에는 계속 지켜보는 프로세스가 없습니다. 정해진 주기로 "들어왔나?" 확인만 할 수 있고, 주기가 곧 지연이 됩니다.

해법. 우리가 물어보는 대신 원장이 우리에게 알려주게 바꿔야 합니다. 그런데 이건 연금시스템팀이 지원해줘야 가능합니다.

PM이 할 일. 연금시스템팀에 "잔고 반영 시 우리 쪽으로 통보를 보내줄 수 있는가"를 물어야 합니다. 답이 "불가"면 60초 요구를 완화하는 PRD 변경이 필요하고, 그건 PM의 결정입니다.

3부 · 제약 충돌

나머지 다섯 건

해결됨 충돌 03 · 04 · 05

03 — 0.3초 재계산. 인출액 슬라이더를 움직일 때마다 서버에 다녀오면 느립니다. 계산 코드가 순수 모듈로 격리돼 있어서 같은 코드를 브라우저에서도 돌립니다. 단, 제출할 때는 반드시 서버에서 다시 계산해 검증합니다.

04 — DB 접속 폭증. 서버리스는 요청마다 인스턴스가 뜨고, 각자 DB에 접속하면 한도를 넘습니다. 커넥션 풀러를 거치게 해서 해결했습니다.

05 — 배치 중복 실행. 밴드 재계산이 두 번 돌면 같은 날 값이 달라집니다. "오늘 아직 갱신 안 된 것만" 처리하도록 조건을 걸어서, 두 번 돌아도 두 번째는 대상이 0건이 되게 했습니다.

개발 차단 충돌 06 — 전문 수신 경로

예탁결제원이 보내는 진행 전문을 받아야 이관 단계를 추적할 수 있습니다. 그런데 우리 서비스는 인터넷 주소에 있고, 금융 전용망으로 오가는 전문을 직접 받을 수 있는지 확인되지 않았습니다. 중계해줄 내부 시스템이 있는지 물어야 합니다. 답이 없으면 기능1의 핵심을 구현할 수 없습니다.

출시 판정 충돌 07 — 퍼블릭 클라우드

Vercel과 Supabase는 외부 클라우드 서비스입니다. 금융회사의 실제 운영 환경에는 망 구성·데이터 소재지 같은 추가 요건이 적용될 수 있습니다. SRS-002는 이 판단을 하지 않고 기록만 했습니다. 학습·검증 목적이면 문제없고, 실제 출시에는 정보보호·법무 검토가 별도로 필요합니다.

3부 · 제약 충돌

"개발을 막는가" vs "출시를 막는가"

이 구분을 못 하면 프로젝트가 통째로 멈춥니다. PM이 가장 자주 쓰게 될 판단 틀입니다.

Blocks Development

답이 없으면 지금 코드를 못 씁니다. 만들 대상 자체가 불분명하니까요.

이 프로젝트: 2건
전문 수신 경로 · 본인 인증 수단

Blocks Release

개발은 진행할 수 있습니다. 다만 답 없이 고객에게 내보낼 수 없습니다.

이 프로젝트: 3건
60초 알림 · 응답 시간 실측 · 규제 적합성

왜 이 구분이 결정적인가. 미해결 항목을 전부 "차단"으로 묶으면 답을 기다리는 동안 팀이 논다는 뜻이 됩니다. 실제로는 5건 중 3건이 개발과 무관합니다.

SRS-002는 여기서 한 발 더 갔습니다 — 기능2 전체가 법무 판정(LEGAL-Q1)에 걸려 있지만, 기능1은 영향이 없어 단독 출시가 가능하다고 명시했습니다. 하나의 미결 사항이 프로젝트 전체를 볼모로 잡지 않게 만든 것입니다.

PM이 회의에서 쓸 문장.
"이 항목이 지금 개발을 막나요, 출시를 막나요? 개발을 막는다면 무엇을 못 만드나요?"

② 답이 없을 때 뭘 할지가 정해져 있을 것 — SRS-002는 항목마다 "미해결 시 확정 동작"을 적어뒀습니다.
③ 차단 등급이 구분돼 있을 것 — 앞 장의 이야기입니다.

4부 · 운영 관점

엔지니어에게 물어야 할 12가지

기술을 몰라도 좋은 질문은 할 수 있습니다. 아래는 이 문서를 근거로 실제 회의에서 쓸 수 있는 것들입니다.

  1. 이 항목이 지금 개발을 막나요, 출시를 막나요?
  2. 이 규칙을 어기면 어느 단계에서 걸리나요? 코드 작성 때인가요, 운영 중인가요?
  3. 이 기능은 재시도해도 안전한가요? 두 번 눌리면 어떻게 되나요?
  4. 실패하면 어느 방향으로 실패하나요? 안전한 쪽인가요, 위험한 쪽인가요?
  5. 이 숫자는 합격 기준인가요, 알람 기준인가요?
  6. 평균 말고 p95로는 어떻게 되나요?
  7. 이 값의 진짜 출처(Source of Truth)는 어디인가요?
  8. 같은 값이 두 화면에 있는데 다를 수 있나요?
  9. 이건 우리가 정할 수 있나요, 다른 팀에 요청해야 하나요?
  10. 답이 안 오면 어떤 축소형으로 나가나요?
  11. 이 결정을 나중에 되돌리려면 비용이 얼마나 드나요?
  12. 지금 이 판단의 근거가 문서 어디에 적혀 있나요?

4부 · 운영 관점

기술 문서를 받았을 때

SRS-002를 처음부터 읽을 때, 그리고 앞으로 다른 기술 문서를 받을 때 쓰는 순서입니다.

1. 먼저 볼 것 — 이 문서가 무엇을 정하는 문서인가

SRS-002는 "어떻게 만드는가"만 다룹니다. "왜 이 기능이 필요한가"는 PRD에 있습니다. 문서의 역할을 헷갈리면 엉뚱한 데서 답을 찾게 됩니다.

2. 그다음 — 미해결과 충돌부터 읽는다

본문을 처음부터 읽지 마세요. §9 제약 충돌과 §11 Open Questions를 먼저 봅니다. PM이 결정해야 할 것이 거기 다 있습니다.

3. 확인할 것 — 요구사항이 조용히 바뀌지 않았는가

기술 문서가 "구현이 어려우니 요구사항을 줄였다"고 하는 경우가 있습니다. SRS-002는 §10.1에 "삭제·완화·해제한 것이 없다"를 명시적으로 확인해뒀습니다. 이 확인이 없는 문서는 직접 대조해야 합니다.

4. 마지막 — 판정과 근거가 일치하는가

SRS-002의 판정은 "조건부 착수 가능"입니다. 그리고 무엇이 막고 있는지, 어디까지 착수 가능한지를 §13.3에 표로 적어뒀습니다. 판정만 있고 근거가 없으면 그 판정은 신뢰할 수 없습니다.

4부 · 운영 관점

이 문서가 잘 쓰인 이유

앞으로 다른 기술 문서를 평가할 때 기준이 됩니다.

좋은 특징SRS-002에서
기술 선택의 대가를 숨기지 않음충돌 7건을 별도 장으로 격리. "완화 가능"과 "잔여 위험"을 나눠 적음
못 정하는 것을 정한 척 안 함PRD에 없는 값은 TBD로 남기고 누가 정해야 하는지 명시
요구사항과 구현을 섞지 않음신규 생성은 기술 규약 51건뿐. 기능 요구사항 0건
판단이 필요한 자리를 미리 없앰Server Action / Route Handler 판정표 같은 기준 제공
규칙을 도구로 강제타입·DB 제약으로 위반 자체를 차단
차단 등급을 구분개발 차단 2건과 출시 차단 3건을 분리

반대로, 이런 문서는 의심해야 합니다.

기술 선택의 단점이 하나도 안 적혀 있거나 · 미해결 항목이 "추후 협의"로만 되어 있거나 · 요구사항이 슬쩍 완화됐는데 그 사실이 표시돼 있지 않거나 · 판정만 있고 근거가 없는 문서.

마무리

이제 원본을 읽을 수 있습니다

SRS-002의 1,124줄 중 PM이 실제로 판단해야 하는 부분은 §9(충돌 7건)와 §11(미해결 7건), 그리고 §13(판정)입니다. 나머지는 필요할 때 찾아보면 됩니다.

다음에 배우면 좋은 것

  • 상태 머신 — PRD §8.6의 상태 전이표. 이 제품의 심장입니다
  • 트레이드오프 읽기 — 모든 기술 선택에는 대가가 있습니다. 그걸 찾는 눈
  • SLO 협상 — 목표 숫자를 정하고 못 지킬 때 조정하는 판단
  • 데이터 계보 — 값 하나가 어디서 와서 어디로 가는지 추적하는 법

기억할 한 가지. 기술 문서를 읽는 목적은 기술을 아는 것이 아니라 결정을 내리는 것입니다. 모르는 용어가 나와도, "이게 우리 결정에 영향을 주는가"만 판단할 수 있으면 충분합니다.
