## 0. 이 문서를 언제 쓰는가

표준안(57일)으로 못 맞추는 외부 기한이 있을 때만 쓴다. **평시에는 표준안을 쓴다.**

압축은 공짜가 아니다. 이 문서는 "45일에 되는가"가 아니라 **"45일에 하려면 무엇을 내주는가"** 를 계산한다.

> **먼저 확인할 것.** 기한이 정말 고정인가? 이 프로젝트는 **기능1과 기능2를 분리 출시할 수 있다**(SRS-002 §13.2 — LEGAL-Q1은 기능2만 막는다). 범위를 줄이는 것이 인원을 늘리는 것보다 거의 항상 싸다. §6에서 다룬다.

**압축안이 표준안보다 인·일이 적다(315 < 342).** 기간이 짧아 유휴가 줄기 때문이다. 인원 1명을 더 쓰는데 총 비용은 오히려 낮다 — 압축안이 이 프로젝트에서 **효율 최적점**이다.

### 1.1 dev5에서 멈춰야 하는 이유

| 인원 | 기간 | 추가 1명의 효과 |
| --- | ---: | --- |
| dev 4 | 57일 | — |
| **dev 5** | **45일** | **−12일** |
| dev 6 | 45일 | **0일** |
| dev 7 | 45일 | 0일 |
| dev 8 | 39일 | −6일 (가동률 67%로 급락) |

**dev5 → dev6은 기간이 전혀 줄지 않는다.** 6번째 인원은 놀 자리밖에 없다. 인원을 더 쓰려면 dev8까지 가야 6일이 줄지만, 그때는 가동률이 67%로 떨어지고 동시 작업 11건의 통합 부담이 생긴다.

**결론: 5명이 실질 상한이다.**

### 1.2 왜 39일 밑으로 못 가는가

임계 경로가 39일이기 때문이다. **인원과 무관한 물리적 하한**이다.

```
FR-001 ─3d→ FR-003 ─3d→ FR-005 ─6d→ FR-007 ─6d→ FR-019 ─3d→ FR-020 ─6d→ FR-021 ─6d→ FR-022
  3d         6d          12d         18d         21d          27d         33d          39d  ← 누적
```

이 8건은 **앞이 끝나야 뒤가 시작된다.** 8명을 붙여도 FR-005는 FR-003 없이 못 시작한다.

| 구간 | 소요 | 줄일 수 있나 |
| --- | ---: | --- |
| FR-001 → FR-003 스캐폴딩·Prisma 구성 | 6일 | 병합 태스크 → **내부 분할 시 단축 여지 있음** |
| FR-005 → FR-007 스키마 16종 · RLS | 12일 | H 2건. 분할 어려움 |
| FR-019 → FR-020 Action 기반 · 멱등 | 9일 | 멱등 처리는 DB 제약 의존 — 분할 위험 |
| FR-021 → FR-022 saveDraft · submitTransfer | 12일 | H 2건. **submitTransfer는 차단 태스크** |

**39일을 깨려면 임계 경로 위 H 태스크를 쪼개야 하는데**, 이들은 도메인 계산·트랜잭션·동시성이라 쪼개면 검증 단위가 무너진다. §6에서 다룬다.

### 1.3 최소 인원 도출

| 제약 | 요구 인원 |
| --- | ---: |
| 총 개발 공수 214일 ÷ 45일 | 4.8 → **5명** |
| 총 디자인 공수 73일 ÷ 45일 | 1.6 → **2명** |
| W4 동시 착수 18건 (최대 폭) | 5명이면 4웨이브에 걸쳐 소화 |
| 동시 작업 최대 7건 | dev5 + des2 = 7 — 정확히 일치 |

**dev5/des2가 45일의 최소 편성이다.** 이보다 적으면 45일에 못 끝내고, 많아도 안 빨라진다.

## 5. 45일보다 더 줄이려면

### 5.1 인원으로는 안 된다

dev8/des3까지 늘려야 39일이고, 그마저 **하한이라 더는 안 줄어든다.** 가동률 67%·동시 11건의 대가를 치르고 6일을 산다. 권하지 않는다.

### 5.2 임계 경로를 깨는 방법

| 방법 | 단축 | 위험 |
| --- | ---: | --- |
| FR-001을 내부 분할해 후행 조기 착수 | ~2일 | 낮음. **권장** |
| FR-005 스키마를 기능1/기능2로 분할 | ~3일 | 중. 관계 정의가 흩어진다 |
| FR-020 멱등 처리를 Action별로 분산 | ~3일 | **높음.** 공통 규약이 깨지면 중복 처리 사고 |
| FR-022를 차단 해제 전 스텁으로 선구현 | 0일 | 무의미. 인증 규격이 바뀌면 재작업 |

**안전하게 얻을 수 있는 건 2일 남짓이다.** 43일이 현실적 최단이며, 그 아래는 검증 단위를 훼손한다.

### 5.3 범위로 줄이는 방법 — 이게 답이다

| 축소안 | 제외 태스크 | 단축 | 근거 |
| --- | ---: | ---: | --- |
| **기능2 후속 릴리스로 분리** | 7건 (FR-043~049) + 디자인 5건 | **약 8일** | SRS-002 §13.2 — LEGAL-Q1이 기능2만 막는다. **구조적으로 분리 가능** |
| F2-06 타명의 조회 제외 | FR-049 · UX-017 | ~1일 | 정적 + 딥링크. 독립성 높음 |

**기능2를 분리하면 45일이 아니라 37일에 기능1을 낼 수 있다.** 그리고 이건 인원을 늘리지 않는다.

> **압축을 검토하기 전에 이걸 먼저 검토해야 한다.** LEGAL-Q1이 아직 미해결이라 **기능2는 어차피 지금 출시할 수 없다.** 완성해 놓고 법무 판정을 기다리는 것과, 판정 후에 만드는 것 중 무엇이 나은지는 사업 판단이다.

## 6. 권고

**1순위 — 범위 분리를 먼저 검토한다.**
기능2를 후속 릴리스로 분리하면 표준 편성(dev4/des2)으로도 **기능1을 약 49일에** 낼 수 있다. 인원 추가 없이. LEGAL-Q1 미해결 상태에서 기능2를 완성해 두는 것이 정말 필요한지 먼저 확인한다.

**2순위 — 범위가 고정이면 압축안(dev5/des2 · 45일).**
표준 대비 12일 단축, 인·일은 오히려 27 적다. 단 아래 셋을 반드시 함께 적용한다.

| # | 필수 동반 조치 |
| :---: | --- |
| 1 | **외부 요청을 D+0에 발송.** OPEN-TEC-004 기한이 D+22로 당겨진다 |
| 2 | **W3 유휴 2명에게 FR-016 시험 코드 선작성** 배정 |
| 3 | **대외 공표는 53일** (계산값 45 + 버퍼 8) |

**하지 말 것 — dev6 이상 투입.**
6번째 개발자는 기간을 1일도 줄이지 않는다. 인·일만 45 늘어난다.
