## 0. 이 문서를 언제 쓰는가

표준안(63일)으로 못 맞추는 외부 기한이 있을 때만 쓴다. **평시에는 표준안을 쓴다.**

압축은 공짜가 아니다. 이 문서는 "45일에 되는가"가 아니라 **"45일에 하려면 무엇을 내주는가"** 를 계산한다.

> **먼저 확인할 것.** 기한이 정말 고정인가? 이 프로젝트는 **기능1과 기능2를 분리 출시할 수 있다**(SRS-002 §13.2 — LEGAL-Q1은 기능2만 막는다). 범위를 줄이는 것이 인원을 늘리는 것보다 거의 항상 싸다. §6에서 다룬다.

### 1.2 왜 45일 밑으로 못 가는가

임계 경로가 45일이기 때문이다. **인원과 무관한 물리적 하한**이다.

```
FR-001 ─3d→ FR-003 ─3d→ FR-005 ─6d→ FR-007 ─6d→ FR-019 ─3d→ FR-020 ─6d→ FR-021 ─6d→ FR-022 ─6d→ FR-052
  3d         6d          12d         18d         21d          27d         33d          39d          45d  ← 누적
```

이 9건은 **앞이 끝나야 뒤가 시작된다.** 8명을 붙여도 FR-005는 FR-003 없이 못 시작한다.

| 구간 | 소요 | 줄일 수 있나 |
| --- | ---: | --- |
| FR-001 → FR-003 스캐폴딩·Prisma 구성 | 6일 | 병합 태스크 → **내부 분할 시 단축 여지 있음** |
| FR-005 → FR-007 스키마 16종 · RLS | 12일 | H 2건. 분할 어려움 |
| FR-019 → FR-020 Action 기반 · 멱등 | 9일 | 멱등 처리는 DB 제약 의존 — 분할 위험 |
| FR-021 → FR-022 saveDraft · submitTransfer | 12일 | H 2건. **submitTransfer는 차단 태스크** |
| FR-022 → FR-052 전이 통합 시험 | 6일 | **줄이면 검증을 포기하는 것** |

**마지막 구간을 줄이자는 제안이 나오면 거부한다.** 상태 전이 통합 시험 없이 출시하면 "완료된 건이 진행 중으로 돌아가는" 회복 불가 사고를 못 잡는다.

## 5. 45일보다 더 줄이려면

### 5.1 인원으로는 안 된다

**dev6이 이미 하한 45일에 도달했다.** dev7·dev8을 넣어도 1일도 줄지 않고 인·일만 45~135 늘어난다. 인원으로 얻을 것이 남아 있지 않다.

### 5.2 임계 경로를 깨는 방법

| 방법 | 단축 | 위험 |
| --- | ---: | --- |
| FR-001을 내부 분할해 후행 조기 착수 | ~2일 | 낮음. **권장** |
| FR-005 스키마를 기능1/기능2로 분할 | ~3일 | 중. 관계 정의가 흩어진다 |
| FR-020 멱등 처리를 Action별로 분산 | ~3일 | **높음.** 공통 규약이 깨지면 중복 처리 사고 |
| FR-022를 차단 해제 전 스텁으로 선구현 | 0일 | 무의미. 인증 규격이 바뀌면 재작업 |

**안전하게 얻을 수 있는 건 2일 남짓이다.** 43일이 현실적 최단이며, 그 아래는 검증 단위를 훼손한다.

### 5.3 범위로 줄이는 방법 — 이게 답이다

| 축소안 | 제외 태스크 | 단축 | 근거 |
| --- | ---: | ---: | --- |
| **기능2 후속 릴리스로 분리** | 12건 (FR-043~049 · UX-013~017) | **표준 편성에서 9일** (63 → 54일) | SRS-002 §13.2 — LEGAL-Q1이 기능2만 막는다. **구조적으로 분리 가능** |
| F2-06 타명의 조회 제외 | FR-049 · UX-017 | ~1일 | 정적 + 딥링크. 독립성 높음 |

**기능2를 분리해도 하한 45일은 그대로다.** 임계 경로(FR-001 → … → FR-022 → FR-052)가 전부 기능1·공통 사슬이기 때문이다.

다만 **표준 편성(dev4/des2)에서는 63일 → 54일로 9일이 줄어든다.** 인원 추가 없이 얻는 단축이다. 공수가 311 → 261일로 50일 감소해 같은 인원이 더 빨리 소화한다.

> **압축을 검토하기 전에 이걸 먼저 검토해야 한다.** LEGAL-Q1이 아직 미해결이라 **기능2는 어차피 지금 출시할 수 없다.** 완성해 놓고 법무 판정을 기다리는 것과, 판정 후에 만드는 것 중 무엇이 나은지는 사업 판단이다.

## 6. 권고

**1순위 — 범위 분리를 먼저 검토한다.**
기능2를 후속 릴리스로 분리하면 표준 편성(dev4/des2)으로 **기능1을 54일에** 낼 수 있다. 인원 추가 없이 9일 단축이다. LEGAL-Q1 미해결 상태에서 기능2를 완성해 두는 것이 정말 필요한지 먼저 확인한다.

**2순위 — 범위가 고정이면 압축안(dev6/des2 · 45일).**
표준 대비 18일 단축, 인·일은 오히려 18 적다. **하한에 도달하는 유일한 편성**이다. 단 아래 셋을 반드시 함께 적용한다.

| # | 필수 동반 조치 |
| :---: | --- |
| 1 | **외부 요청을 D+0에 발송.** OPEN-TEC-004 기한이 **D+16**으로 당겨진다 |
| 2 | **W3 유휴 2명에게 FR-051 시험 매트릭스 선착수** 배정 |
| 3 | **대외 공표는 54일** (계산값 45 + 버퍼 9) |

**하지 말 것 — dev7 이상 투입.**
7번째 개발자는 기간을 1일도 줄이지 않는다. 인·일만 45 늘어난다. **dev6이 하한이다.**
