## 1. 결론

**축약은 타당하게 수행되었다. 다만 기대했던 효과와 실제 효과가 다르다.**

| 지표 | v1 (102건) | v2 (66건) | 변화 |
| --- | ---: | ---: | ---: |
| 태스크 수 | 102 | 66 | **−36** |
| 총 공수 (1인 환산) | 356일 | 284일 | −72일 |
| **최단 기간 (임계 경로)** | **36일** | **39일** | **+3일** |
| 위상 깊이 | 9단계 | 8단계 | −1 |
| H 복잡도 | 30 | 30 | 0 |

**축약은 기간을 줄이지 않았다. 오히려 3일 늘렸다.**

이것이 이 검증의 핵심 발견이다. 태스크 수가 36% 줄었는데 최단 기간은 늘어났다. 이유는 §4에서 다룬다.

> **그래서 축약이 잘못이었나 — 아니다.** 축약의 실제 이득은 기간이 아니라 **관리 오버헤드**에 있다. 티켓 102개를 운영하는 비용과 66개를 운영하는 비용은 다르다. 다만 **"태스크를 줄이면 빨라진다"는 기대는 틀렸다**는 것을 기록해 둔다.

## 2. 축약이 가능했던 구조적 이유

축약 여지는 태스크 목록이 부실해서 생긴 게 아니라, **SRS-002의 산출물 구조가 원래 묶여 있었기** 때문에 생겼다.

| 구조 | v1에서 흩어진 방식 | 실제 산출물 |
| --- | --- | --- |
| `lib/adapters/` | 어댑터 4건이 각각 태스크 | 파일 4개, 동일 패턴, 같은 커밋 단위 |
| `components/domain/` | 표기 컴포넌트 6건이 각각 태스크 | SRS §6.2 한 절, 한 세트 |
| §5.3 스키마 제약 | CHECK·WORM·unique 3건이 각각 태스크 | **하나의 마이그레이션 SQL 파일** |
| 초기 셋업 | 프로젝트·Supabase·Vercel·환경변수·Tailwind 5건 | 리포 초기 커밋 + 인프라 프로비저닝 2회 작업 |
| 인접 라우트 | `/withdrawal` 과 `/withdrawal/recipient` 별건 | 같은 세그먼트, 연속 플로우 |

**L 복잡도 20건 중 18건이 여기 해당했다.** 단독 티켓으로 두면 "환경 변수 등록" 같은 반나절짜리가 스프린트 보드를 채운다.

## 3. 병합 원칙

셋 중 **하나를 만족할 때만** 병합했다. "둘 다 M이니까"는 근거로 쓰지 않았다.

| # | 원칙 | 적용 사례 |
| --- | --- | --- |
| 1 | **같은 파일·모듈** | FR-017 어댑터 3종 · FR-035 표기 컴포넌트 6종 |
| 2 | **SRS 같은 절의 한 산출물** | FR-006 스키마 제약 3종 (§5.3 = 마이그레이션 SQL 1개) |
| 3 | **인접 라우트** (부모·자식 또는 같은 세그먼트 형제) | FR-042 `/transfer/[id]/basis`+`/completion` · FR-043 `/withdrawal`+`/recipient` |

### 3.1 병합하지 않은 것 — 네 가지 이유

| 태스크 | 복잡도 | 병합하지 않은 이유 |
| --- | :---: | --- |
| **H 30건 전부** | H | 절대 조건. 도메인 계산·트랜잭션·상태 판정은 각각 독립 검증 대상이다 |
| FR-019 Server Action 공통 기반 | M | **H 4건(FR-020~023)의 선행.** 묶으면 H 착수가 늦어져 임계 경로가 길어진다 |
| FR-026 Route Handler 인증 공통 | M | H 2건(FR-027·028)의 선행 |
| FR-030 배치 공통 가드 | M | H 2건(FR-031·032)의 선행 |
| FR-018 예탁결제원 어댑터 | M | **차단 태스크.** 다른 어댑터 3종과 묶으면 멀쩡한 것까지 함께 막힌다 |

> **"H의 선행인 M은 병합하지 않는다"가 이 축약의 숨은 규칙이다.** 병합 자체는 원칙 1을 만족해도, 그 결과가 임계 경로를 늘리면 축약의 목적에 반한다. FR-019를 다른 M과 묶었다면 FR-020~023 네 건이 전부 지연됐을 것이다.

## 4. 왜 기간이 늘었는가 — 축약의 역설

### 4.1 임계 경로가 이동했다

| 버전 | 임계 경로 | 성격 |
| --- | --- | --- |
| **v1 (36일)** | UX-001 → UX-002 → UX-004 → UX-008 → UX-012 → UX-021 → FR-063 → FR-064 | **디자인 사슬** |
| **v2 (39일)** | FR-001 → FR-003 → FR-005 → FR-007 → FR-019 → FR-020 → FR-021 → FR-022 | **백엔드 사슬** |

v1에서는 **디자인 트랙이 개발을 막고 있었다.** 디자인 태스크가 잘게 쪼개져 길게 연결돼 있었기 때문이다. v2에서 디자인 29건을 17건으로 묶자 디자인 사슬이 짧아졌고, **백엔드 사슬이 드러났다.**

이건 축약의 부작용이 아니라 **진짜 병목이 드러난 것**이다. v1의 36일은 디자인 세분화가 만든 인위적 경로였다.

### 4.2 병합된 태스크가 길어졌다

축약이 기간을 늘린 직접 원인은 단순하다. **L 3건을 묶으면 M 1건이 된다.**

| 사례 | v1 | v2 | 경로상 소요 |
| --- | --- | --- | --- |
| FR-001 리포 스캐폴딩 | 舊 001(L) + 006(L) + 016(M) | FR-001 (M) | 1일 → **3일** |
| FR-003 Prisma 구성 | 舊 003(M) + 007(M) + 010(L) | FR-003 (M) | 3일 → 3일 |

임계 경로 위에서 L이 M으로 승격되면 그만큼 경로가 길어진다. **경로 밖이면 무해하고, 경로 위면 손해다.**

### 4.3 공수 −72일은 모델 산물이다

**총 공수 감소를 실제 절감으로 읽으면 안 된다.**

이 계산은 복잡도별 소요를 `L=1일 · M=3일 · H=6일`로 가정한다. 병합 태스크에는 M(3일)을 부여했다. 그래서 L 6건을 묶으면 6일이 3일로 계산된다 — **작업량이 줄어서가 아니라 라벨이 바뀌어서다.**

| 실제로 줄어드는 것 | 실제로 줄지 않는 것 |
| --- | --- |
| 티켓 작성·리뷰·상태 전환 오버헤드 | 코드를 쓰는 시간 |
| 스프린트 플래닝 시간 | 시험 작성 시간 |
| 의존성 추적 부담 | 리뷰 시간 |

**정직한 표현: 공수는 그대로고 관리 비용만 줄었다.** §6의 권고는 이 전제 위에 있다.

## 7. 권고

**v2(66건)를 실행 기준으로 삼되, 세 가지를 함께 적용한다.**

### 권고 1 — v2를 실행 기준으로

관리 오버헤드 감소가 3일의 기간 손실보다 크다. 특히 **임계 경로가 백엔드로 명확해진 것**이 계획 수립에 유리하다. v1은 추적용으로 보존한다.

### 권고 2 — 임계 경로 위 병합 태스크는 내부 분할

FR-001은 임계 경로의 첫 태스크이면서 병합 태스크다. **티켓은 하나로 두되 체크리스트로 내부를 쪼개** 매일 진척이 보이게 한다. [tasks-full/](./tasks-full)의 Task Breakdown 항목이 이 역할을 한다.

### 권고 3 — 더 이상 축약하지 않는다

66건에서 더 줄이려면 성격이 다른 태스크를 묶거나 H를 건드려야 한다. 둘 다 손해다.

| 추가 축약 시도 | 결과 |
| --- | --- |
| 화면을 기능 도메인 단위로 묶기 | 태스크 하나가 2~3주 → 진척률이 보이지 않음 |
| H 병합 | 독립 검증 불가 — 계산 오류가 다른 기능에 묻힌다 |
| H 선행 M 병합 | 임계 경로 연장 |
